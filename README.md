# Debate Tab App — setup guide

This zip is a hand-written Flutter scaffold, not a generated project — because
the sandbox that built it has no Flutter SDK and no access to pub.dev. You'll
run the actual `flutter create` step yourself, locally, then drop these files
in. That's steps 1–2 below; everything after that is normal.

## 0. Prerequisites

- Flutter SDK installed (`flutter --version` should work)
- A Firebase account (console.firebase.google.com)
- Node.js installed, for the Firebase CLI

## 1. Create the real Flutter project

```bash
flutter create debate_tab_app --platforms=android,web
cd debate_tab_app
```

## 2. Drop in this scaffold

Copy everything from this zip **into** the project `flutter create` just made,
overwriting `lib/main.dart` and `pubspec.yaml`:

```
debate_tab_app/          <- the one `flutter create` made
├── android/              <- keep (from flutter create)
├── web/                  <- keep (from flutter create)
├── lib/                  <- REPLACE with this zip's lib/
├── pubspec.yaml          <- REPLACE with this zip's pubspec.yaml
├── firebase.json         <- ADD (new)
├── firestore.rules       <- ADD (new)
└── firestore.indexes.json <- ADD (new)
```

## 3. Create the Firebase project and connect it

```bash
npm install -g firebase-tools
firebase login

dart pub global activate flutterfire_cli
flutterfire configure
```

`flutterfire configure` will:
- let you pick or create a Firebase project in the browser
- ask which platforms to register (choose Android + Web)
- **overwrite `lib/firebase_options.dart`** with real values

That placeholder file I included deliberately throws an error if it's still
in place — that's your signal `flutterfire configure` hasn't been run yet.

In the Firebase console, also turn on:
- **Authentication → Sign-in method → Email/Password**
- **Firestore Database → Create database** (start in production mode; the
  rules file below handles access control)

## 4. Deploy the security rules

```bash
firebase deploy --only firestore:rules
```

## 5. Create your first admin user

Registration isn't self-service on purpose — roles are assigned, not chosen
(see the note in the chat about why). For your first login:

1. Firebase console → Authentication → Add user → enter an email/password.
2. Firestore console → start collection `users` → document ID = **that user's
   UID** (copy it from the Authentication tab) → add fields:
   - `email`: same email
   - `displayName`: your name
   - `role`: `admin`

## 6. Run it

```bash
flutter pub get
flutter run -d chrome     # or -d <android-device-id>
```

You should land on the login page, sign in with the account from step 5, and
land on the (stub) admin console.

## Folder structure

```
lib/
├── main.dart                 # Firebase init, runs the app
├── app.dart                  # MaterialApp.router + theme
├── firebase_options.dart     # generated by flutterfire configure
│
├── core/                     # cross-feature, no domain knowledge
│   ├── theme/app_theme.dart
│   ├── router/app_router.dart     # role-based redirect logic lives here
│   └── widgets/loading_view.dart
│
└── features/                 # one folder per Tabbycat domain module
    ├── auth/
    │   ├── domain/            # plain Dart models (AppUser, UserRole)
    │   ├── data/               # talks to Firebase (AuthRepository)
    │   ├── application/        # Riverpod providers (state)
    │   └── presentation/       # widgets/pages (LoginPage, SplashPage)
    ├── tournaments/
    │   ├── domain/             # Tournament model, TournamentFormat enum
    │   ├── data/                # TournamentRepository (Firestore CRUD)
    │   ├── application/         # tournament list / single-tournament providers
    │   └── presentation/        # list, create/edit form, dashboard shell
    ├── adjudicator/presentation/ # stub — home shell for adjudicator/team
    └── public/presentation/    # stub — no-auth tab site shell
```

Every feature we build next (`tournaments`, `participants`, `draw`, `motions`,
`ballots`, `feedback`, `standings`) follows the same
`domain / data / application / presentation` split as `auth/` did. That's the
whole pattern — once you've read `auth/`, you've read the shape of every
feature to come.

## What's actually wired up right now

- Email/password sign-in (`LoginPage`)
- Firebase Auth state + Firestore role lookup, kept live (`auth_providers.dart`)
- Router redirect that sends signed-in users to `/admin`, `/adjudicator`, or
  `/public` based on their Firestore role — and blocks navigating to a route
  your role doesn't own (`app_router.dart`)
- Firestore rules enforcing that same role model server-side, not just in the
  app (`firestore.rules`)
- Full tournament CRUD: list (`/admin`), create (`/admin/tournaments/new`),
  a dashboard shell (`/admin/tournaments/:id`), and edit
  (`/admin/tournaments/:id/edit`) — this is also the pattern every
  tournament-scoped feature below will follow, reading `tournamentId` from
  the route the same way

## What's a stub, on purpose

`AdjudicatorHomePage` and `PublicHomePage` currently just show a placeholder.
The tournament dashboard (`TournamentDashboardPage`) shows six disabled tiles
(Participants, Venues, Draw, Motions, Ballots, Standings) marking exactly
where the next features attach — same folder pattern as `tournaments/`, new
feature folders sitting next to it.

## One design note worth knowing before you build further

Firestore rules above deliberately do **not** let the public read
`debates` directly, even though the tab site needs to show draws. Unreleased
results living in a document that's also readable by anyone is a common way
tournaments accidentally leak sensitive results early. The intended pattern:
a Cloud Function copies a debate into a separate `publicDraws` collection
only once the round is marked released — that function is a good next build
target once the draw feature exists.
